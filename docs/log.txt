@printfdebugging                           Sat Sep 19 11:35:27 AM IST 2026                       *log.txt-2026-09-19-1135*

   usually when trying to upgrade a function from just a prototype which works just to show something, to something
   which really works well, we should focus more on the data flow through that function. what a function can assume
   happened before it, what it has to check and re-evaluate. what is expected from a function given all those pieces
   of information. and when we have those things listed, that's usually the way the should be written down. we get
   the data, we calculate some values, we check some flags and we claculate and store the new data which is the
   purpose of the function we are working on.

   the data pipeline is at the heart of the software. what happens at each pass comes in only later once we have
   got the pipelines right. this doesn't mean that we should prototype for 30 days and then start writing code.
   but it means that "given we know all the constructs we have to do something and most of the unknowns, we should
   spend more thought on how the data flows, more than we usually do". That makes life/refactors/implementation so
   much easier.

@printfdebugging                           Wed Sep 16 06:33:29 AM IST 2026                       *log.txt-2026-09-16-0633*

   I was wrong in the last thing I wrote here. Sometimes the arcitecture is so messy that it's not sanely possible
   to iterate over things one step at a time. The LineRenderer renders one line at a time, the shader takes
   uniforms to draw a line, layouting happens on a per line basis (which is fine), we store VAOs/VBOs per line. If
   the whole API is designed that way, it's extremely hard to think of even the next two steps to make the
   situation any better.

   In such cases, it's better to create parallel types _Buffer, _BufferRenderer etc and then the equivalents fo
   the methods.. and then you use the last API's code as the stuffing for the new API/methods.. And when the new
   one works, you replace the old ones with them. Hopefully I am not wrong again ;). Abstraction is a necessary
   evil.

@printfdebugging                           Sun Sep  6 02:21:09 AM IST 2026                       *log.txt-2026-09-06-0221*

   The codebase evolves gradually, and if you as a developer are able to see 10 steps ahead where the code is in a
   much better condition/arcitecture, then there's this temptation to just put the existing code away in a temporary
   file and start afresh. That's not how it works. That often leads to messy commits where you break things and
   then spend time figuring out what went wrong.. And this is in general part of a larger tendency of running away
   from things, from a mess which you created in the first place (usually).

   The way out of it is to beat the codebase into shape one hammer at a time, one bend at a time.. One who can see
   10 steps ahead, with some effort, can also put down 10 simple steps to reach there. All 10 steps might not come
   to you in one go, but all you need is a direction and 1-2 steps in vision..

   This way, the code still works at the end of each step. The throw away approach is bad because doing 10 things
   at the same time creates another mess, often much worst than what you had before that..

                        READING & UNDERSTANDING ~
- In these times, it's easy to reach out for an LLM to externalize
  your thinking and we are trying to not do that here. Then how do fix
  an error which seems really hard and you don't have any clue about
  it?

- This is no different than using a library for the first time, or
  exploring a new area of the codebase. You must UNDERSTAND what's
  going on. That takes time, but it's fine, there's no substitute for
  that. Spend some hours reading the documentation, taking notes,
  making arrow diagrams on paper... all that is often necessary when
  you are trying to understand something very complex. Spend time with
  the problem and UNDERSTAND it.

- Once you understand the problem, the rest becomes easy, you now have
  an overview of what's going on and reading also reveals a number of
  potential fixes, so now it's about choosing the best fix for the
  problem, that's not simple, still far less overwhelming then the
  first problem.

- To understand, you must READ properly, don't just gloss over the
  prose looking for keywords.. Over time, you build an intuition about
  where you might find the solution, the official documentation, some
  github readme, or maybe some article on the topic, in the decreasing
  order of value I guess.

                        RENDERING MULTIPLE LINES ~
- I need abstractions for that. For a renderer which just stores the
  visible quads, I would need a reLayout function of some sort & that
  means I need some abstractions around the harfbuzz code for
  re-shaping the lines..

- Created a `struct Editor` to store the editor state & a `struct Layout`
  to store the layouting/relayouting/shaping logic, though most of
  that is yet to be moved to `layout.c` functions.

- I now face the same problem as before, `layout.c` functions need
  access to the editor object and vice-versa & when we add the
  renderer to the mix, everything accesses everything else. So I would
  need some kind of wrapper object, but I wonder if that would lead me
  down the abstraction hell (I just came out of).

  |https://github.com/printfdebugging/editor|
  |https://github.com/printfdebugging/engine|
  |https://github.com/printfdebugging/external|

- Thinking more about it, I realized that I was treating the file
  boundaries (editor.c/layout.c) as a hard wall which the objects
  cannot cross, but the `Layout` object doesn't exist in vacuum, it's
  editor's layout. So it should be more like editorReLayout than
  reLayout.. >c
        void editorReLayout(struct Editor *editor); // good
        void reLayout(struct Layout *layout);       // bad

- The file boundary might help decide how much of the state should be
  accessed and in what way (readonly/read-write).
